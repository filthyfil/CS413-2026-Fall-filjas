# LAMBDA Workbench: an MVC web front-end for LAMBDA

A local, single-user web page for loading, editing, linting and
interpreting LAMBDA programs written as `d0exp` constructor expressions.
The page uses classic MVC in plain JavaScript. A small Python/Flask server
on `127.0.0.1` provides the language tools from the supplied `lambda1.py`.
See [ARCHITECTURE.md](ARCHITECTURE.md) for the design and
[TESTING.md](TESTING.md) for verification.

## Setup, start and test

From the `MySolution/` directory:

```sh
python3.12 -m venv .venv                     # any Python >= 3.12
.venv/bin/pip install -r requirements.txt    # Flask and pytest
.venv/bin/python -m server                   # start the server
```

Open **http://127.0.0.1:5000/**. Stop the server with Ctrl+C.
Use `.venv/bin/python -m server --port 8000` if port 5000 is busy.
On Windows, use `.venv\Scripts\python` instead of `.venv/bin/python`.

Run the tests:

```sh
.venv/bin/pytest          # Python: reader, free variables, lint, interpret, HTTP layer
node --test               # JavaScript: finds tests/js/*.test.js (Model, Controller, HttpBackend)
```

## Using the page

1. **Load source.** Choose File uploads a local UTF-8 text file. Manual input
   opens a blank editor. Factorial (canned) and Fibonacci (canned) load
   editable examples. The page shows the applied source's name and revision.
2. **Edit.** Changes stay in the editor until you click **Apply changes**,
   which creates a new revision and clears the old results.
   **Discard changes** goes back to the applied source. While you have
   unapplied changes, the tool buttons and the Load source menu are
   disabled. Edits only change the page's copy, never the original file.
3. **Actions**, in order: **Lint**, **Interpret**, **Type-check**,
   **Compile**, **Execute**. **Stop** cancels a running Interpret.
   **Retry** appears after a failure or a stop.
4. **Results** list the action, the source revision and the outcome as text,
   followed by the message and any value.

## Demonstration

Each step lists what to do and what you should see. The files used are in
`samples/`.

1. **Factorial.** Click *Factorial (canned)* and then *Interpret*.
   You should see `Interpret · revision 1 · Success` and
   `D0Vint(arg1=3628800)`. Click *Lint*: `No free variables found.`
2. **Fibonacci.** Click *Fibonacci (canned)*, which creates revision 2 and
   clears the results, then *Interpret*. You should see
   `D0Vint(arg1=610)`.
3. **Undeclared variable, then fixed.**
   * Click *Manual input*, type `D0Evar("x")`, *Apply changes*, then
     *Lint*. You should see `Lint · revision 3 · Error (undeclared
     variables)`, `Undeclared variable(s): x`.
   * Edit the text to `D0Elet("x", D0Eint(5), D0Evar("x"))`, *Apply
     changes*, then *Lint*. You should see revision 4 and
     `No free variables found.`
   * Click *Interpret*. You should see `D0Vint(arg1=5)`.
4. **Lint passes, but the program fails at runtime.** Choose File →
   `samples/div_zero.txt`. *Lint* reports `No free variables found.`, but
   *Interpret* reports `Error (runtime)`,
   `Runtime error: ZeroDivisionError: integer division or modulo by zero`.
   Lint only checks that every variable is declared, so a closed program
   can still fail when it runs. `samples/type_error.txt` shows the same with
   a `TypeError`.
5. **Placeholders.** *Type-check* gives `Not implemented`,
   `Type checking is not yet implemented.` *Compile* gives `Not implemented`,
   `Compilation is not yet implemented.` *Execute* stays disabled, and the
   note under the buttons explains that it runs code generated by Compile and
   that no generated artifact exists for this revision because compilation
   is not yet implemented.
6. **Stop and retry.** Load `samples/infinite_loop.txt` and click
   *Interpret*. The status reads `Status: busy — Interpret is running on
   revision N…` and the other controls are disabled. Click *Stop*: the
   result is `Stopped`, the controls come back, and *Retry Interpret* is
   offered.

## Supported input

* Exactly one constructor expression of type `d0exp`, using the
  constructors from `lambda1.py`: `D0Eint, D0Ebtf, D0Eop1, D0Eop2, D0Evar,
  D0Elam, D0Efix, D0Eapp, D0Eif0, D0Elet, D0Epair, D0Epfst, D0Epsnd`.
  No imports are needed.
* Arguments may be positional or keyword (`D0Eint(arg1=-5)`). Allowed
  literals are integers (including negative ones), `True`/`False`, and
  strings for variable names and operator names.
* Operators: `D0Eop1` takes `+1` or `-1`. `D0Eop2` takes
  `+ - * / < > <= >= == !=`.
* Comments (`# …`), blank lines, indentation and line breaks are allowed.
* The input is read by a restricted reader (`server/reader.py`). It parses
  the text with Python's `ast` module and accepts only the constructors and
  literals above, checking every argument. Nothing in the input is ever run
  as Python, so `__import__("os")…` is rejected as input
  (`samples/not_allowed.txt`).
* Uploads must be valid UTF-8 text.

## Limits

* **Source size:** at most **1 MB** (1,000,000 bytes of UTF-8). Empty or
  whitespace-only source is rejected. Rejected changes leave the applied
  source untouched, and rejected edits stay in the editor so you can fix
  them.
* **Execution:** there is no fixed timeout. Each Interpret runs in its own
  Python child process, and **Stop** kills it immediately, so a
  non-terminating program cannot leave the app permanently busy. Starting a
  new Interpret also stops any run left over from before, and stopping the
  server stops everything.
* **Recursion:** the child process raises Python's recursion limit to
  100,000 and runs on a 512 MB stack, so programs such as `fact(5000)` work.
  Recursion beyond that is reported as a runtime error.

## Known limitations

* Nesting depth is limited by Python's parser to about 200 nested
  constructor calls. Deeper input is rejected as an input error.
* The application's state lives in the page and is lost when you reload or
  close the tab. Only one user and one browser tab are supported.
* Starting the interpreter process adds roughly 0.1–0.5 s to each Interpret.
* Type-check and Compile are placeholders, and Execute is disabled until a
  compiler exists. ARCHITECTURE.md describes how they would be connected.
* The server is Flask's development server. It is bound to the loopback
  interface and is not meant for public hosting.

## Reflection

> **Draft:** written by the AI assistant from this project's design
> discussion. The author should rewrite it in their own words.

MVC helped most where the assignment's rules interact. Revisions, unapplied
edits, the busy state, the artifact and stale results all affect each other,
and keeping them in one Model with no DOM and no network made those
interactions small, explicit methods. Each rule could be tested in Node in
milliseconds, without a browser. The observer link (View subscribes to
Model) removed a whole class of bugs: no event handler updates the page
"by hand", so the page always shows what the Model contains. The backend
interface paid off in the same way. The Controller test can substitute a
fake backend that holds, throws or gets cancelled on demand. That made
busy-state, failure and retry behavior easy to test, and the View did not
change at all.

Separation was hardest at the edges. File upload is partly a browser
concern (the `File` object) and partly a rule (UTF-8 and size), so the
Controller decodes and the Model validates. The 1 MB limit is duplicated in
JavaScript and Python because each side has to protect itself. Stopping a
run cut across every layer: a Stop button in the View, a run id in the
Controller, an abort in the adapter and a process kill on the server. A
thread could not be stopped at all, which forced the child-process design.

The architecture makes adding a real compiler easy. The buttons, dispatch,
result rendering and the Model's artifact rules (bound to a revision,
cleared on change, required by Execute) already exist. A compiler only needs
to implement `LanguageTools.compile` and `execute` on the server and return
an artifact in the documented format.
